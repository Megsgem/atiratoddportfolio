About the Game

Time Frame: 11 days

Team Size: 1

Language/Engine Used: C#, Unity

Main Contributions:

- Data Persistence
- Fishing Mechanic
- Shop System and Currency
- Bait System

This is a game I made for the Fishing Horror Jam in 2025. This was a jam where fishing had to be a main mechanic of the game and there had to be a horror element to it as well. I made the entire game on my own over the course of the jam (11 days) including doing all the programming for the game.

The game is set in the fictional place of Stillwater Lake, somewhere which seems normal on the surface but, after fishing around, you'll start to uncover some of its secrets. It is a fishing simulator game and I used C# and Unity to program all of the mechanics and features of the game such as the guide book feature, the shop system and currency, bait and the fishing mechanic itself.

Data Persistence

For certain features of this game - namely the guide book and the shop system - I needed certain pieces of data to persist across scenes.

In the guide book, I wanted the pictures of the fish to simply be the shape of the fish if the player hadn't yet caught that kind of fish yet but this would change to show what the fish actually looks like once the player had caught at least one of that kind of fish. Since the player is able to access the guide book in both the 'Lake' scene and the 'Lakeside' scene, I needed the data of which fish the player has caught to persist from scene to scene.

In order to do this, I first created a new scriptable object which I used to store information about the player. In this scriptable object, I created an array variable which would store the kinds of fish that the player had caught at least once. Since this only one instance of this scriptable object would exist in the game, I made the array variable a static variable, meaning that only one instance of this array would exist in the game as well. This meant that the data about what fish the player had caught would be the same from scene to scene. When the player catches a fish of a certain type for the first time in the 'Lake' scene, the name of that type of fish is added to the array in the scriptable object and therefore the guide book in both the 'Lake' scene and in the 'Lakeside' scene is able to check this array and know which fish the player has caught and set the fish's picture in the guide book accordingly.

Since the player earns money when they catch fish in the 'Lake' scene, but can only spend that money in the 'Shop' scene, I needed the amount of money the player currently has to be accessible in both scenes and thus this data also needed to persist across scenes. Another piece of data that needed to persist across scenes was the amount of each kind of bait the player had as this would be changed when the player bought more bait in the shop but would be used in the 'Lake' scene. To do this, I used a similar method to how I'd made the data needed for the guide book to persist: by adding three more static variables to the scriptable object I'd already created to store information about the player. These variables were for storing the amount of money the player had, the amount of worms the player had and the amount of fish the player had. The fact that these variables were static once again meant that their values would be the same across scenes and since there would only be one instance of the scriptable object for the information about the player in the game, then using static variables wasn't necessarily a problem. Since these variable's values would be the same across scenes, the player could now earn money by catching fish in the 'Lake' scene and spend that money in the shop and the player could also by bait (fish and worms) at the shop and use these for fishing in the lake.

While the way I am currently implementing data persistence works for the game as it is at the moment, there are some things I may change about this in the future as I do plan on working on the game further. I am currently using static variables to store the pieces of data that I need to persist across scenes but this may become less feasible if I add more data that needs to persist (e.g. if I add more kinds of bait the amount the player has of each kind of bait will need to persist across scenes). However, I do know that there are other ways of implementing data persistence in Unity such as using the DontDestroyOnLoad function to make sure an object isn't deleted when a new scene is loaded. The main reason I am not using this particular approach currently is because the object I wouldn't destroy would likely be the player as this is the object that most of the data that needs to persist relates to however, an actual player object isn't needed in either the 'Lake' scene or the 'Shop' scene. I could still use this approach in the future by doing something like creating a new game object that would only be used to store the information that needs to persist but I am unsure if this is the approach I would take. If I were to keep using statics, I may change the way the code is structured slightly so that rather than using a scriptable object to store the data that persists across scenes, I may instead create a static class which would store the data as this would work in largely the same way as the code I am using currently since the scriptable class contains only static variables so far. However, if I do expand the game, it is unlikely that I will continue to use this approach as it will become less feasible the more data there is that needs to persist across scenes.

Fishing Mechanic

The main mechanic of this game is the fishing mechanic since the theme of the jam meant that fishing had to be a central part of the game. The fishing mechanic has many different parts to it such as casting the fishing line, reeling in the fish and calculating how much money the player earned based on the fish they caught. When creating this mechanic, I broke the overall problem down into smaller sections so that I could tackle it easier which made creating this mechanic fairly simple.

The first part of this mechanic that I created was the coroutine I used for what happens when the player presses the 'Cast' button in order to cast their line when they begin fishing. This coroutine first waits for a random amount of seconds between 2 and 8 seconds and then the 'Reel' button (that the player uses to successfully reel in a fish) is enabled so the player can reel the fish in. I made it wait this random amount of time to simulate the time it would take for the player to hook a fish so that the mechanic would have a slightly more realistic feel. Once the 'Reel' button has been enabled, the coroutine then waits another second to give the player time to respond and press the 'Reel' button to reel the fish in but if once that second had passed the player hadn't yet pressed the 'Reel' button, the 'Reel' button would be disabled again and the rest of the UI elements involved in the fishing mechanic (e.g. the images of the fishing rod or the 'Cast' button) would be reset to what they were before the 'Cast' button was pressed.

The second part of the fishing mechanic that I made was the 'CatchFish' function as well as the 'CheckIfCaught' and 'AddToCatches' functions that would be used within the 'CatchFish' function. The first one of these functions that I made was the 'CheckIfCaught' function which iterates through the array of the types of fish that the player has caught already and checks whether the name of the fish that the player has reeled in is in this array already and then returns true or false depending on the result. The next function I made was the 'AddToCatches' function which simply resizes the array which stores the types of fish the player has caught by one and then stores the string which is passed in to the function in the last entry of the array. I created these functions first as both of them would be used in the actual 'CatchFish' function. This function has the name of a fish passed in to it and firstly it calls the 'CheckIfCaught' function to see if this fish has been caught by the player before and, if it hasn't, then the 'AddToCatches' function is called so that the name of the fish can be added to the array. As well as this, this function calculated the number that the amount of money the player earns from catching a fish is multiplied by with the multiplier being 1.5 if the player has never caught that kind of fish before and the multiplier being 1 if the fish has been caught before. This multiplier is then returned from the function so that the amount of money the player earns from catching a fish can be calculated in the 'GenerateFish' function.

The next part of this mechanic that I started working on was the way to randomly generate which fish has been caught. In order to create the functionality for this, I first created an enum which I used to store the different kinds of fish that are currently in the game with there currently being 8 values within the enum. Then, I created the function for generating which fish has been caught by the player. This function generates a random number between 0 and 7 using Unity's built-in Random library and then uses a switch statement to check the random number that is generated and which type of fish in the enum has the same value. Then, once the kind of fish being caught had been generated, the image of the fish on the hook is set to the correct type of fish, the 'CatchFish' method is called and the player's money is increased by the correct amount depending on the type of fish that has been caught and whether the player has caught that kind of fish before. Finally, the name of the fish that has been generated is returned from this function.

The final things I made in order to create the fishing mechanic were the functions that would be called when the 'Cast' and 'Reel' buttons are pressed. These functions would mostly use the functionality I had already created in the previously mentioned functions to actually make the fishing mechanic itself work and allow the player to use it. The first thing the function for the 'Cast' button does is reset the boolean value which stores whether a fish has been reeled in to false and then sets the UI related to the fishing mechanic to be in the appropriate states (e.g. disabling the other buttons in the 'Lake' scene and then disabling the 'Cast' button itself so it couldn't be pressed again). It then starts the 'Cast' coroutine that I had previously created. The function for the 'Reel' button first sets the boolean value storing whether a fish has been reeled in to true and then uses the 'GenerateFish' function to generate the kind of fish that is being reeled in. The 'Reel' button is then disabled and a message is displayed congratulating the player on catching that kind of fish. I then also made a function that would reset all of the UI related to the fishing mechanic back to what it was before the player used the mechanic meaning that the displayed message as well as the fish on the hook disappears and the 'Cast' button is once again enabled so that the player is able to fish again.

What I Learned

One of the things working on this jam made me consider more was data persistence and how it can be implemented and used. The way I have currently implemented data persistence in this game works fine for the way the game works currently but thinking about how I may extend this game in the future made me consider other ways of implementing data persistence that may work better.

Making this game and participating in this game jam also really highlighted to me the importance of breaking a larger coding problem such as certain mechanics of a game down into more manageable tasks. This is something that I had been doing and was familiar with even before working on this project and it is something that I have continued to do since but the time constraints of this game jam made me do this to a further extent than I had in many of my previous projects and it highlighted how much more streamlined this made the coding process as it was not only easier to visualise and solve the overall problem but it was also much easier to debug the code when it was created this way.
