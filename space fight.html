About the Game

Time Frame: 8 weeks

Team Size: 1

Language/Library used: C#, Monogame

Main Contributions:

- Client-Server Model for Data Transmission
- Data Replication Across the Network
- Basic Lobby System
- Packet Encryption and Security
- Score System
- TCP and UDP

This is a game that I made as part of the Multiplayer Games Module that I took in my second year of university. Over the course of creating this game, I worked with multithreading to create a networked game and used a server-client model to allow multiple players play the game with each other. I was given a framework as part of this module which contained a basic game scene as well as the things within this scene such as game objects but I built upon this framework to create my own game and created the functionality for the server, clients and data transmission which allowed the game to be played across a network by multiple users at once.

The game is inspired by games such as Space Invaders and is a relatively simple 2D shooter game set in space where the players must destroy all the enemy ships before they themselves are defeated. As well as this, if the players defeat the enemies and win, the players are presented with a leaderboard showing which of them achieved the highest score.

Data Replication

Data replication is when data is transmitted from one client on a network to another and is very important for multiplayer games as it is essential for the experience of the players that they all see and experience the same world state. While creating this game, there were many pieces of data that I needed to replicate across the clients connected to the server and during the process of implementing ways to do this, I encountered various different problems when replicating the different pieces of data which I had to solve.

One of the main things that I needed to replicate across the different clients playing the game was data to do with the ships that the players control. Each player controls one ship but in order to make sure the players experience the same world state, they will also need to see the other ship's actions in real time as the other players control them.

The first thing I did in order to facilitate this was to create a new packet class which would be sent across the network from one client to another and would contain information related to the position of a ship as well as the ID of that ship. Whenever one of the players moves their ship, a position packet is sent across the network via a UDP message and this position packet will update the other clients in the network about that player's ship's position. I decided to do this via a UDP message rather than a TCP one as UDP is a connectionless communication protocol and therefore doesn't need to establish a connection with each client before sending the packet. This is good for broadcasting data across a network to all connected clients which is what I needed to do for this project. When the server recieves a position packet from one client, it will then send it to the other clients on the network and when these clients recieve this position packet, they will invoke the action for what should happen if a ship moves. Currently, this action is bound to a function which sets the position and rotation of the RemoteShip object with the same ID as the ship that is moving to be the ones passed in to the function which are the ones contained within the position packet. These RemoteShip objects can only be moved in this way and are used to show a player the position and rotation of the other players' ships.

In order to defeat the enemy ships, the players are able to fire bullets at them and therefore every player needs to see the bullets that the other players fire. This was a problem that was somewhat more difficult to solve than replicating the movement of the other players' ships as not only did the replicated bullet have to move in the same direction as the bullet that was fired but it also had to be spawned at the correct place at the correct time. I also didn't want to take a similar approach to the one I had taken when replicating the ships' movement - by creating a 'RemoteBullet' class and sending position packets across the network every time a bullet's position changed - as the bullets are constantly moving and therefore position packets are going to have to be continuously sent through the network, potentially for many bullets at a time. Instead, I decided to take a different approach which I felt would be better for my project.

Instead of using a position packet, I created a new type of packet called a 'bullet packet' which would contain information about the bullet fired by the player such as its velocity and start position as well as the ID of the ship that fired it. These bullet packets are sent from one client each time a player fires a bullet and are sent to the server which then sends the packet to the rest of the clients. Once a client has recieved a bullet packet from the server, it will invoke the action bound to the firing of a weapon. This action will call the Fire function of the weapon component attached to the remote ship with the same ID as the ship that fired the bullet and this Fire function will spawn a bullet with the same starting position, rotation and velocity as the one fired by the player on the replicated client. This means that bullets fired by players should appear on all clients and move in the same way across all of them, assuming that the world state is the same for all clients. I used this approach of prediciting the bullet's movement on the replicated client using data about its starting position, rotation and velocity as this requires only one packet to be per bullet and therefore reduces the amount of work the server and clients have to do.

There were other pieces of data in my project that had to be replicated such as the players' scores for the score system and the number of clients connected to the game as part of the lobby system. These pieces of data were replicated in similar ways to the other pieces of data that are replicated across clients: by using a new type of packet as a way to transmit the data and, when recieved by the server from one of the clients, sending this packet to all other connected clients. The biggest issue I had with replicating these pieces of data across clients was figuring out when exactly to send the data from one client to another as doing this at different moments could affect the outcome. For example, I initially tried to send the packet containing data about the updated number of clients connected to the server immediately after each client connected to the server. However, this wouldn't work and the text on the other clients which displayed the current number of clients connected wouldn't change. I found that to solve this, the packet had to be sent after the client had logged in to the game and sending the data at this point would update the text on the other clients. Similarly, when sending the packet containing the data about a player's score, I initially tried sending it once the game had ended for all players however, I realised that this wouldn't work as the clients had disconnected from the game at this point. To solve this, I instead sent this data as soon as the conditions for the player's game ending were met (the player dies, their time runs out or all enemies are defeated) but before the game's state for that player had been changed to 'Ending'. This meant that once a player's game ended, the other players would recieve their score and thus it would be able to be displayed on the score board on that client once the game has ended for them too. In the end, I didn't use this particular method of replicating the player's scores as I decided that they should have a combined score as a team instead of individual scores as I felt it would be better for the teamwork aspect of the game but I still learned a lot from solving this issue. Currently, the players' team score is replicated across clients and is updated on all clients whenever a player defeats one of the enemies.

What I Learned

This project was the first time I had encountered multithreading and building networked games and over the course of working on this project I learned a lot about both of these things as well as the solutions to the new and unique challenges they presented and many of the things I learned when working on this project are things I will use in the future.
